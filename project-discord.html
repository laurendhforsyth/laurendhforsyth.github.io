Discord Audio Broadcasting Bot

A Discord bot built with JavaScript and discord.js to broadcast audio to voice channels.

The implementation includes environment-based configuration, voice channel joining, audio playback controls and diagnostics for monitoring player state.

Overview

Task: A scalable, multi-instance Node.js audio broadcasting system designed to relay a high-quality voice stream across up to 12+ Discord channels simultaneously.

Role: Systems Architect & Developer

Tech Stack: Node.js, Discord.js (v14), @discordjs/voice, PM2

The Architecture

Building a bot to join a voice channel is straightforward. Building a synchronized fleet of 13 bots requires a robust architectural approach to audio routing and process management. The system is split into two core components:

  • The Master Broadcaster: A primary client that listens for slash commands, joins the user's active voice channel, and captures their incoming audio stream using an Opus-encoded AudioResource.
  • The Repeater Fleet: 12 independent worker clients managed concurrently.

Instead of processing and piping the audio 12 individual times—which would severely bottleneck CPU and memory—the Master feeds a single globalAudioPlayer. The 12 workers then simply subscribe to this global player. This fan-out architecture ensures near-zero latency between channels, regardless of how many repeaters are deployed.

Slash Commands

/broadcast - Connects the broadcaster and 12 repeaters to the voice channels.

/broadcastonly - Only connects the repeaters to the voice channels without the broadcaster required.

/endbroadcast - Ends the broadcast and disconnects all the bots from the Discord server.

PM2 & Its Involvement

Running 13 concurrent Discord client connections within a single application demands rock-solid stability, as well as keeping all 13 bots up and running 24/7 as much as possible with little to no interaction. While Node.js is excellent at handling asynchronous network operations, a single unhandled exception or a sudden Discord API timeout could crash the process, dropping the broadcaster and all 12 repeaters simultaneously.

To mitigate this risk, the deployment relies on PM2, an advanced production process manager for Node.js. Rather than running the bot in a fragile, active terminal session, PM2 daemonizes the application, ensuring it runs persistently in the background.

Integrating PM2 solved several key deployment challenges:

  • Zero-Downtime Recovery: If the script ever encounters a fatal error or memory leak, PM2's auto-restart functionality instantly reboots the process, bringing the entire fleet back online without manual intervention.
  • Environment Management: Securely handling 13 distinct bot tokens is complex. PM2 securely and consistently injects the required environment variables (MASTER_TOKEN, WORKER_1 through WORKER_12) directly into the production environment.
  • Resource Monitoring: By utilizing the pm2 monit dashboard, I can track the fleet's memory footprint and CPU usage in real-time—a crucial capability when managing the overhead of 13 active Opus audio streams.

Because this project was for personal usage, I transferred the PM2 manager onto a separate computer where I can remote in, rather than running it on my personal computer. Running it on my personal computer comes with certain risks, some of the most obvious being if my computer decides to update overnight and restarts at 6am, all the bots will be down until 4am the next day, which is unacceptable. It also uses up my personal computer resources, while this way the bots are essentially being hosted on a server somewhere - except in this case the server is another computer in my house.

Iteration & Problem Solving

During development, getting the bots connected was only half the battle. The core challenges revolved around optimization and user experience.

Optimizing the Startup Sequence

A core project requirement was ensuring the 13 bots appeared at the very top of the voice channels for easy visibility. Because Discord sorts alphabetically and recently blocked special characters (like ! or _) in base bot usernames, I had to rely on server nicknames to force them to the top.

For servers the bots were already in, kicking and re-inviting them to update permissions was impractical. Instead, I leveraged the servers' default nickname permissions and ran a one-off loop to prepend an underscore to their names (e.g., changing "Broadcaster" to "_Broadcaster"). This immediately bumped them to the top of the UI.

The challenge then became automating this for any future servers the bots joined without bottlenecking the system. Running an auto-nickname check during the startup loop for 13 simultaneous PM2 instances would hammer the Discord API and risk severe rate-limiting.

To solve this, I stripped the nickname logic out of the boot sequence entirely and bound it exclusively to the guildCreate event. Now, each bot requests its _ nickname exactly once - the moment it joins a new server. This keeps the startup sequence incredibly lightweight and completely eliminates redundant API calls. 

// Auto-Nickname Workers (Executes strictly on server join to prevent redundant API calls)

for (let i = 1; i <= 12; i++) {

  const worker = new Client({ intents });

  worker.on("guildCreate", async (guild) => {

    try {

      await guild.members.me.setNickname(`_Repeater ${i}`);

      console.log(`Worker ${i} successfully nicknamed itself in ${guild.name}`);

    } catch (error) {

      console.log(`Note: Missing permissions to nickname Worker ${i}`);

    }

  });

  worker.login(process.env[`WORKER_${i}`]);

  workerBots.push(worker);

}

Refining the User Experience

Command spam is a major issue with multi-bot systems. Traditional prefix commands (e.g., !broadcast) leave lingering text in the server's channels that are available for everyone to see regardless of who used the command, degrading the chat experience for standard users. To solve this, I migrated the entire control schema to Discord's native Slash Commands. By utilizing the interactionCreate event, the system can now respond with ephemeral: true flags. This pivot means administrators can deploy and recall the entire 13-bot fleet silently. The server text channels remain perfectly clean, and the command feedback is localized entirely to the user controlling the broadcast. 

// Silent deployment via Ephemeral replies

if (interaction.commandName === "broadcast") {

  // ... deployment logic ...

  return interaction.reply({

    content: `Fleet deployed. Broadcaster in **${masterChannel.name}**, repeaters cascading downward. Type **/endbroadcast** to disconnect them.`,

    ephemeral: true,

  });

}

Testing Process

Initial testing was handled locally by running the application directly from the terminal. This brought the entire 13-bot fleet online within a dedicated test server, while also keeping them available in the production server for larger scale load testing. To validate the audio routing, I would join the primary voice channel and initialize the broadcast command. Using an alternate account on Discord Canary in a secondary voice channel, I could speak into my primary microphone and monitor the repeater output in real time to ensure latency remained low and audio quality was high.

After establishing stable local performance, I migrated the project to a secondary remote machine for persistent background hosting via PM2. This setup provided a highly efficient iterative workflow. To implement updates, I would pause the remote PM2 process, run the bots locally for development and testing, and then deploy the finalized code back to the remote machine. A quick PM2 restart would then bring the upgraded fleet back online.

Outcomes & Next Steps

Building this 13-bot broadcasting fleet was a rigorous exercise in concurrent process management. The project required navigating the specific intricacies of the @discordjs/voice lifecycle, particularly when managing persistent audio subscriptions with manual end behaviors. It also highlighted the critical importance of resource cleanup, ensuring that all 13 active voice connections are gracefully destroyed upon command to prevent memory leaks and hanging background processes.

While the core application is built and ready to use, there are a few loose ends to wrap up before official deployment:

  • Cross-Server Termination: I am updating the /endbroadcast logic so that it successfully disconnects the repeater bots from all active servers simultaneously, rather than just the server where the command was originally issued.
  • Final Stress Test: I will conduct one last large scale load test to verify audio latency and overall system stability under full capacity.

Once these final adjustments are implemented, the broadcasting system will be completely operational.
